# Event-name FTS validation

Measured on Windows on 2026-10-08, using release-mode synthetic stores. Builds used
`CARGO_BUILD_JOBS=4`; UI tests used `--maxWorkers=2`. The initial read/backfill
measurements ran alongside other validation processes and are report-only
observations. The write gate and scoped-miss report below each ran alone on the
otherwise idle machine. These synthetic measurements do not establish live-game
acceptance.

## Change and coverage

Migration 012 creates `event_fts` with `unicode61` tokenization, source rowids,
insert/update/delete triggers and a backfill. Malformed legacy JSON remains in
`instance_events`; its unavailable names are not indexed. Migration registration,
latest-version assertions and historical downgrade fixtures now account for v12.

Event pages use the existing quoted prefix-term builder and a parameterized FTS
rowid subquery. A bounded `EXISTS` probe returns an empty page immediately for a
name absent from the whole store. Otherwise, the FTS rowid list filters the
kind-index scan; the default four-kind query sorts the matches before applying
the page limit.
A name that exists globally but is excluded by kind, range or opener scope still
requires the page query. The per-kind UNION is removed;
kind/range/run/dungeon/opener filters, cursor ties, row/byte limits and query-free
summaries remain covered by store tests.

`event_search_matches_each_name_field_and_escapes_like_metacharacters` was renamed
`event_search_matches_name_prefixes_and_ignores_punctuation`: the old literal
`%`, `_` and backslash substring expectations now return all rows in scope,
matching Chat when no searchable terms remain. It also asserts
that `Vex` matches and `xlin` does not. The mixed-kind cursor/tie test now uses
`Vex`, including duplicate kind filters. The synthetic UI event preview now uses
name-token prefixes, with a new test for prefixes, fragments and hostile punctuation;
no Svelte views or chat/alert search implementations changed.

New FTS tests cover a real v11 migration with existing and malformed rows,
idempotence, insert, upsert, rowid/name update, valid-to-malformed update, cutoff
delete, whole-table delete, index integrity and prefixes/quoted operators across
all five fields using valid event variants. Existing NUL and query-bound tests
remain intact. The original unreadable-event test passes unmodified. There is no
production event-retention deletion path in this checkout; cutoff and full-table
SQL deletion are covered, not a nonexistent retention API.

`EXPLAIN QUERY PLAN` for the existence probe, on both stores (rechecked in the
F4 measurements below using the production SQL builder and shared probe SQL):

```text
SCAN CONSTANT ROW
SCALAR SUBQUERY 1
SCAN event_fts VIRTUAL TABLE INDEX 0:M5
```

The FTS virtual-table access uses MATCH. When the probe returns false, the
instance-event page query is not executed. For a matching probe, both stores use:

```text
SEARCH e USING INDEX instance_events_kind (kind=?)
LIST SUBQUERY 1
SCAN event_fts VIRTUAL TABLE INDEX 0:M5
CREATE BLOOM FILTER
USE TEMP B-TREE FOR ORDER BY
```

## Name present but excluded by scope

The updated `portal_heavy_event_reads` report also searches for `Synthetic` with
`kinds: [portal_opened]` on the 200k store. This name exists in the death/boss
fields, so the global FTS existence probe is asserted true, but none of the 60k
portal events has a matching opener. The first page took **48.2179 ms** and returned
zero rows, no cursor and no entered-run matches. This report ran alone on the
otherwise idle machine.

Its page-query plan is:

```text
SEARCH e USING INDEX instance_events_kind (kind=?)
LIST SUBQUERY 1
SCAN event_fts VIRTUAL TABLE INDEX 0:M5
CREATE BLOOM FILTER
```

The probe does not bypass this scoped miss: the FTS rowid list filters the
kind-index scan. This single-kind query does not require the temporary ordering
B-tree shown for the default four-kind query above.

## F4 size, few-hit search and SQL provenance (2026-10-09)

Release report commands:

```powershell
$env:CARGO_BUILD_JOBS='4'
cargo test --release --locked -p maxed-store --test d_perf event_history_volume_reads -- --ignored --nocapture
cargo test --release --locked -p maxed-store --test d_perf portal_heavy_event_reads -- --ignored --nocapture
```

The 1.2M-event fixture changes five spread-out observations to the synthetic name
`RareSyntheticPlayer`: three departures and two portal openings. Total cardinality
stays 1.2M. These are the only two portal openings in this departure-heavy fixture,
so the Key pops result does not characterize a portal-heavy kind-index scan.
The first `list_events` call for each scope used limit 50, no cursor and no range.
These are single report-only samples after setup/backfill, not cold-cache or p95
measurements. UI checks overlapped fixture construction but had finished before
backfill and measured reads; no other builds or tests from this session ran during
those measurements.

| Scope | Matching rows | First page |
| --- | ---: | ---: |
| Default four event kinds | 5 | 116.3477 ms |
| Key pops (`portal_opened`) | 2 | 0.2545 ms |

Both pages had no next cursor and stayed below the requested 1 s stop threshold.
The v11-to-v12 backfill took **4.8665211 s**. The no-match first page took
**3.5883 ms** and the broad `SynthAl` first page (50 rows) took **234.7353 ms**;
that prefix now matches the other 1,199,995 observations.

For disk cost, the report checkpoints/truncates the WAL before and after the
migration, reads the main-file length, and calculates allocated bytes as
`(page_count - freelist_count) * page_size`. It does not run `VACUUM`.

| Measurement | Before migration 012 | After backfill | Added |
| --- | ---: | ---: | ---: |
| Checkpointed database file | 944,631,808 B | 996,671,488 B | 52,039,680 B (49.63 MiB) |
| Allocated database pages | 944,631,808 B | 993,001,472 B | 48,369,664 B (46.13 MiB) |

This is the whole-database migration delta, including FTS shadow tables and
migration/schema metadata, rather than a sum of FTS table payloads alone. The
file increase is about **5.51%**; 3,670,016 bytes in the resulting file are free
pages. Migration 012 retains its regular-content FTS layout and checksum; this
follow-up records the cost without changing the schema.

The event-page EXPLAIN helper calls the thin `event_page_sql_for_tests` wrapper
around the production `event_page_sql` builder used by `list_events`, including
production bindings and validation. The `event_fts_probe_for_tests` wrapper returns
the production `EVENT_FTS_PROBE` SQL and a binding built by production `fts_query`;
`list_events` uses that constant and term builder directly.
These doc-hidden integration-test seams follow the existing store convention;
there is no hand-copied event-page SQL or prefix-term builder in the harness.
The actual plans reproduce the probe and default/single-kind plans quoted above:
the five-hit default page includes the temporary ordering B-tree, while the
single-kind Key pops page does not. Timing still calls `list_events`, including
its existence probe and entered-run lookup.

The 200k portal-heavy rerun also reproduced the quoted plans: no-match page
**0.6401 ms**, matching `Vex` page **30.9189 ms**, and a globally present name
excluded by Key pops scope **23.4734 ms**. Its all-time summary took 270.1156 ms
(above the existing 250 ms target); this follow-up does not alter summary queries
or any performance threshold.
