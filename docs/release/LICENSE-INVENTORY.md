# Distribution and licence inventory

This inventory covers Maxed 0.1.0's Windows x64 NSIS package, including embedded
code and assets. [distribution-inventory.json](distribution-inventory.json) is
the machine-readable inventory of **11 stable extracted payload files**, each
with exactly `file`, `license` and lowercase `sha256`. Installer-private
`$PLUGINSDIR/` entries are extracted support files, not persistent application
files. The metadata schema permits only that literal prefix plus one filename;
all ordinary paths retain the existing validation rules.

`maxed.exe` is deliberately excluded from the static inventory: its hash changes
on every build. The verified build's `bundle-manifest.json` records its actual
packed hash, the original build hash and the verified Tauri bundle-type marker
offset. Its licensing is covered by [LICENSE](../../LICENSE),
[NOTICE.md](../../NOTICE.md), and
[THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md), all shipped beside it.
This static inventory never substitutes for the final executable/installer
signature and payload checks.

## Regeneration and checks

For release 0.1.4, `@tauri-apps/cli` is pinned exactly to `2.12.1` and excluded
from Dependabot updates. CLI upgrades change the bundled NSIS toolset and the
reviewed installer payload and notices, so upgrades require a deliberate
NSIS/payload review.

The **Notices** workflow (`.github/workflows/notices.yml`) runs the real generator
with `-Check` on PRs to `main` and pushes to `main` when dependency, generator,
vendor or inventory inputs change. A stale notice or pin fails this check.
Review that result before merging dependency changes and before tagging; the
release build retains its own unconditional check.

Maintainers without Windows can recover notices directly from a PR run, even
before this workflow exists on the default branch:

1. When `-Check` fails on a PR or main push, the same job attempts generation
   without `-Check`, then verifies the regenerated bytes with `-Check`.
2. Download the **regenerated-notices** artifact from that **failed run**. It
   contains only `THIRD-PARTY-NOTICES.md`, the generator's only output. The job
   remains failed even when regeneration and upload succeed: the committed
   notices must be fixed before the check can pass.
3. Review and commit that file on the PR branch, then refresh its hash in both
   inventories using the existing instructions below and run the packaging suites.
   The workflow never commits or pushes.

If generation itself fails (for example, an outdated CLI version or DLL hash
pin), its error is printed and no artifact is uploaded. Review and update the
generator pins and inventory provenance first, then push to rerun the check.
The existing Tauri CLI 2.12.1 guard must be reviewed separately for the current
lockfile; regeneration cannot bypass approved version/hash guards.

Manual regeneration remains available once the workflow exists on the default
branch: select **Notices → Run workflow**, choose the PR branch, and set
**regenerate=true**. Download `third-party-notices-<run-id>-<attempt>` from the
successful run, then review/commit and refresh hashes as above. This mode also
verifies with `-Check` before upload; dispatch defaults to check-only. Fork
contributors need a maintainer branch in this repository or the workflow enabled
in their fork for dispatch; ordinary fork PR runs can produce recovery artifacts.

Provisioning uses `npm ci`, `cargo fetch --locked`, and the locally installed Tauri
CLI's unsigned NSIS build, with `createUpdaterArtifacts: false`, `--no-sign`, and
locked offline Cargo arguments. This follows the release bundler's own verified
NSIS downloads and layout at `$env:LOCALAPPDATA/tauri/NSIS`, without duplicating
upstream download pins or requiring signing credentials. The temporary config
leaves the tracked production config intact. It costs a full Windows build;
only Cargo registry/index archives and git sources are cached, with saves limited
to successful main runs. NSIS and compiled outputs are provisioned fresh.
The unsigned installer is only a provisioning byproduct and is never uploaded.

From the repository root, with the locked Cargo source cache, installed locked
npm packages and cached NSIS toolset available:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/New-ThirdPartyNotices.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/New-ThirdPartyNotices.ps1 -Check
```

Output is deterministic UTF-8 without BOM, with LF newlines, ordinal ordering,
content-addressed deduplication and no local paths. `-Check` compares bytes in
memory without rewriting the committed file. A result exceeding 3,000,000
bytes reports its size and stops without writing. Current output is
**2,242,246 bytes**. Embedding the complete Rust attribution required raising
the former 2 MB notices ceiling to 3 MB; the installer retains its separate
20,000,000-byte limit. Verify compressed impact using a fresh signed package;
historical estimates do not certify current installer size. Upstream trailing
spaces are retained verbatim. The two `.gitattributes` `-whitespace` rules
apply only to THIRD-PARTY-NOTICES.md and the vendor notice directory; the
existing `* text=auto eol=lf` normalisation remains unchanged. After
regeneration, refresh its hash in both inventories and run all packaging
suites. `build-release.ps1 -Package` runs the generator's `-Check` after the
Tauri build has provisioned the NSIS toolset and before signature verification
or any bundle manifest, failing on stale notices or absent/modified vendor
texts. `release-build.test.ps1` tests fresh, stale and missing checks using
synthetic build inputs and bundler/Cargo boundaries; it also mutates the
Microsoft and Rust vendor inputs in an isolated fixture, checks the Rust
channel guard, verifies conversion determinism and checks all body wording and
preformatted notices for preservation. `release-metadata.test.ps1` runs this
committed inventory through the real metadata schema with a synthetic
signature-verifier boundary and checks all five repository-sourced payload
hashes.

Windows PowerShell 5.1 generation and `-Check` have run successfully. PowerShell
7.6.6 also passes `-Check` against the same committed bytes. The implementation
uses compatible APIs and explicitly handles PowerShell 5.1's
empty-JSON-property limitation for npm's root package. No new dependencies or
network access are required.
